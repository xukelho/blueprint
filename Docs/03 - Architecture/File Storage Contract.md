# File storage contract

## Domain model

`StoredObject` is the provider-neutral record for one immutable object. Its opaque key is generated by the backend and never contains a user-controlled path. It records the expected upload properties, the verified provider metadata, and the physical deletion lifecycle.

`ProjectDocument` is the project-owned logical document. It must reference exactly one project phase and one `StoredObject`. Moving a document changes only its phase. Replacing content creates a new `StoredObject`, switches the document atomically, and queues the old object for physical deletion. This release intentionally has no version history.

## Lifecycle

- Stored objects: `PendingUpload` -> `Available` -> `DeletionPending` -> `Deleted`.
- A pending upload becomes available only after the object store confirms its size, media type, and optional checksum/ETag.
- Project documents are active or logically deleted. Logical deletion queues their current object for physical deletion.
- Failed storage calls do not advance durable state. Background maintenance retries expired uploads and `DeletionPending` objects.

## Invariants

- Every document and phase belongs to the same project; PostgreSQL enforces this with a composite foreign key.
- A document always has a phase. Phase deletion is restrictive while documents reference it.
- Object keys are unique, server-generated, and provider-neutral.
- Available object content is immutable. Replacement never overwrites a key.
- Download grants are issued only for active documents backed by available objects.
- A phase may be removed only when empty, after an explicit move of all documents, or after explicit logical deletion of all documents.
- Timeline reconciliation preserves phase identity by occurrence of phase code, so repeated phase codes remain supported and reordering does not recreate matched rows.

## Configuration

The `ObjectStorage` section defines `Endpoint`, `Region`, `Bucket`, `AccessKey`, `SecretKey`, `ForcePathStyle`, `UploadGrantLifetime`, `DownloadGrantLifetime`, and `PendingUploadLifetime`. These values describe an S3-compatible service without exposing AWS SDK types outside the adapter. Local Compose uses MinIO and development-only credentials; deployments must inject secrets.

## Non-goals

HTTP endpoints and frontend changes are deferred. General-purpose folders, file version history, and detailed filename/presentation rules are excluded.

## API/UI handoff

The later API should translate `FileService` commands/results rather than expose persistence or AWS SDK types. The client flow is: request pending upload -> upload using the returned PUT grant and required headers -> signal completion -> render the active document -> request short-lived download grants. Replace and delete are explicit commands. Timeline removal must require one of the service's explicit `EmptyOnly`, `MoveDocuments`, or `DeleteDocuments` strategies; never infer a destructive choice.

Service contract:

| Operation | Input | Result / durable effect |
| --- | --- | --- |
| `CreatePendingUploadAsync` | project, phase, file name, media type, byte length, actor | document ID, object ID, expiring PUT grant; persists `PendingUpload` |
| `CompleteUploadAsync` | document ID, actor | verifies remote length/media type and changes the object to `Available` |
| `CreateDownloadGrantAsync` | active document ID | short-lived GET grant; rejects pending/deleted documents |
| `MoveAsync` | document ID, target phase, actor | changes only the phase after same-project validation |
| `CreateReplacementUploadAsync` | document and new upload properties | new immutable object ID and PUT grant; current content remains active |
| `CompleteReplacementAsync` | document, replacement object, actor | verifies and swaps atomically; queues the prior object for deletion |
| `DeleteAsync` | document ID, actor | logical document deletion and physical-deletion queueing |
| `PhaseRemovalService.RemoveAsync` | project, phase, explicit mode, optional target, actor | rejects non-empty implicit removal; explicitly moves or deletes documents before removing the phase |

Expected API mappings are domain validation -> 400, missing or inaccessible aggregate -> 404, unsafe phase removal/state conflict -> 409, and temporary object-store failure -> 503. Upload URLs must be returned with their required headers and absolute expiry; the UI must upload directly, then call completion before treating a document as available. Retries of completion, logical deletion, and background maintenance are safe; replacement initiation may create a new pending object and should use the returned object ID for completion.
